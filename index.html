ThreatSense.

ThreatSense turns a single malware sample into a fully cited Incident Response Action Plan. Containment through hardening, every step traced to NIST or MITRE.

  • RoleSecurity engineer · Playbook author · ML lead · Architect · Designer
  • StackPython · Flask · SQLite · LightGBM · VirusTotal API · pefile

“Incident Response tools stop at identification. Nobody writes the response plan for you.
ThreatSense does.”

The problem

An analyst opens VirusTotal, reads thirty sandbox actions and a tree of MITRE ATT&CK techniques, and stares at the screen. The artifacts are there. The next eight hours are still spent translating them into containment steps, eradication checks, recovery actions, and post-incident hardening, manually, against three different standards documents.

What it does, end to end

  1. 01
    Static analysis & ML. EMBER2024 cross-check, then a LightGBM verdict across six malware families.
  2. 02
    VirusTotal enrichment. Live AV verdicts, sandbox behaviours, and the ATT&CK techniques they triggered.
  3. 03
    Rule engine. 35 self-built deterministic rules map ATT&CK to D3FEND, each cited to NIST, CISA, or NCA.
  4. 04
    Threat scoring. Four signals fold into one severity tier; behaviour carries the most weight.
  5. 05
    IRAP generation. A phase-ordered action plan, rendered as HTML, JSON, and PDF.
  1. 01
    Static analysis & ML. Cross-checks the sample against a local EMBER2024 corpus, then runs its structural features through a trained LightGBM classifier to predict which of six malware families it belongs to.
  2. 02
    VirusTotal enrichment. Pulls live AV verdicts, the sample's observed behaviors inside commercial sandboxes, and the MITRE ATT&CK techniques those sandboxes flagged.
  3. 03
    Rule engine. A self-built deterministic 35-rule engine, authored from scratch, matches the observed techniques against a curated map of ATT&CK → D3FEND countermeasures, with every recommendation traced to NIST, CISA, or NCA guidance.
  4. 04
    Threat scoring. Four signals fold into one severity tier: what the file did, what family it belongs to, what other engines flagged, and how hard it tried to hide. Behavior carries the most weight, because what a sample does is more telling than what it claims to be.
  5. 05
    IRAP generation. A four-phase action plan (containment, eradication, recovery, hardening) covering classification, techniques, IOCs, and citations. Generated once and shaped for three readers: an HTML view the analyst works the incident from, a JSON payload for downstream tooling, and a printable PDF for the post-incident report.

Architecture

The rule engine, live

Pick a technique. The engine returns the matching D3FEND countermeasure, a one-line recommendation, and the standard it cites. SixThree of the thirty-five rules.

Observed technique
T1486 Data Encrypted for Impact Impact tactic · Ransomware
D3FEND countermeasure
D3-NI Network Isolation
Recommendation

Isolate the host immediately. Do not power it off; encryption keys may still be recoverable from memory.

Cited to CISA #StopRansomware Checklist §1

By the numbers

35 Deterministic ATT&CK → D3FEND rules
2,568 EMBER2024 feature dimensions
93.25% LightGBM accuracy · Win32 subset
0.78 Macro F1 across 6 families
4 Graceful degradation modes
8h → 10m Analyst time per sample

Design choices I'd defend in front of a panel

  • No LLMs anywhere in the pipeline. A hallucinated citation is not defensible in front of an auditor.
  • ML as a supporting actor. LightGBM can say which features drove the verdict; black-box accuracy cannot.
  • Four graceful degradation modes. Missing evidence lowers confidence; it is never invented.
  • D3FEND IDs verified three times. Five corrections applied during spec-locking.
  • No LLMs anywhere in the pipeline. The 35 rules are fixed and the citations are real codes. A generative model would draft the same incident two different ways and would occasionally fabricate a NIST or D3FEND ID that resolves to nothing. An IRAP has to be defensible in front of an auditor; a hallucinated one isn't.
  • ML as a supporting actor, not the thesis. A deep-net classifier would likely top the accuracy chart, but LightGBM was chosen because it can tell you which features drove the verdict. That explanation feeds straight into the IRAP's reasoning. Black-box accuracy can't.
  • Four graceful degradation modes. The pipeline draws from several data sources, and some days one of them is unavailable. Rather than failing silently or inventing what it can't see, the system drops to a lower confidence tier, tells the analyst exactly what evidence is missing, and refuses to fabricate the rest.
  • D3FEND IDs verified three times. Five corrections were applied during spec-locking. Citations that look right but resolve wrong are worse than no citations.

The problem

Universities can't keep pace with how fast technology ages. By the time we graduate, a quiet fraction of what we learned has been replaced, deprecated, or flagged as insecure or wrong, and nobody told us until we walk into that job interview.

Stale closes that gap one course at a time, and frames the result as career-relevant evidence against the role we're actually applying for.

A real finding

A search for one student shows every student.

SQL injection · Lecture 6 · Database & Content Providers · pages 9, 22

A student types this in the roll number box: ' OR '1'='1

Slide code Unsafe
Cursor c = db.rawQuery(
  "SELECT * FROM student WHERE rollno='"
    + editRollno.getText() + "'",
  null);

SQL injection risk.This input changes the search and shows every student's record.

Corrected code Safe
Cursor c = db.rawQuery(
  "SELECT * FROM student WHERE rollno = ?",
  new String[]{rollno});

SQL injection prevented.The search looks for that exact text and finds no student.
